## 1. 背景

### 1.1 趋势:从「背知识」到「边推理边检索」

大模型落地正在从"把知识压进参数"转向"**边推理边检索**"的 Deep-Research 范式:面对复杂问题时,模型不再一次性吐出答案,而是**多轮调用搜索工具**,一边检索一边推理,逐步逼近答案。这类"搜索智能体(Search Agent)"是当前最重要的应用形态之一。

### 1.2 为什么用 RL,而不是 SFT

要让模型学会"**何时该搜、搜什么、检索回来的信息如何整合、何时停下作答**",SFT 只能模仿固定轨迹,无法探索决策空间;RL 让模型在与检索环境的交互中试错、按最终答案是否正确获得奖励,是训练这种"决策式"能力的自然选择。Search-R1 已经验证了短程"推理 + 检索" RL 的可行性,本项目在其基础上向长程扩展。

### 1.3 缺口与目标

社区缺一个**既能稳定复现、又能平滑扩展到长程多轮**的开源 RL recipe。SearchAgent-Zero 的目标不是刷单一指标,而是让 Search Agent RL 变得 **reproducible(可复现)、scalable(可扩展到长程)、extensible(可在其上做算法探索)**。

## 2. 痛点

真正的难点不在"能不能搜一两轮",而在**能不能稳定地搜几十轮**。当轨迹从 Search-R1 的 2–6 轮扩展到 BrowseComp-Plus 的 20–40 轮时,一系列问题集中爆发:

| # | 痛点 | 具体症状 |
|---|------|----------|
| P1 | **长程 rollout 会崩** | 基线框架在长多轮轨迹上出现 rollout crash,训练跑不稳、扩不上去 |
| P2 | **上下文预算爆炸** | 每轮检索回来的文档很长,几轮就把 context 填满,无法进行真正的长程搜索 |
| P3 | **异常轨迹污染训练信号** | 重复搜索、单轮并行 query 过多、工具格式错误等噪声,若整条惩罚会"错杀"前面正确的搜索行为 |
| P4 | **异步训练的分布漂移** | 为提高吞吐引入异步后,rollout 策略与 actor 更新不同步,重要性权重方差大,训练易发散 |

下面的方法,每一个都精准对应其中一个痛点。

## 3. 方法

SearchAgent-Zero 分两层:**基础设施层**(让长程 rollout 不崩、跑得快)与**算法层**(让训练信号干净、能扩到更多轮)。四个核心设计如下。

### 设计 1:稳定可扩展的 RL 基础设施(治 P1)

- **是什么**:基于 verl + **AgentLoop** rollout,用 vLLM 异步执行多轮工具调用(`multi_turn.enable=True`,`default_agent_loop=tool_agent`,`rollout.mode=async`)。提供**同步 GRPO** 与 **全异步(fully-async)** 两条训练入口。
- **解决什么**:P1 —— 长程 rollout 崩溃。
- **效果**:能稳定扩展到 20–40 轮的长程搜索轨迹而不崩,消除了基线框架在长轨迹上观察到的 rollout crash。

### 设计 2:搜索结果摘要压缩 self-summary(治 P2)

- **是什么**:每轮检索回来的长文档,先用模型自身压缩成摘要(`enable_tool_response_summary=True`,`summary_use_external_model=False`,`summary_max_tokens=1024`),再放回上下文。
- **解决什么**:P2 —— 上下文预算爆炸。
- **效果**:在固定 context 预算内塞下更多搜索轮次,充分训练后平均检索次数可扩展到约 **38 次**。
- **代价(需诚实说明)**:自摘要会**丢失原文细节、并可能引入摘要幻觉**。本项目的取舍是:牺牲单轮信息保真度,换取"能搜更多轮"的整体覆盖度;下游 Recall 的提升(见 §5)表明在本 benchmark 上这笔交易是划算的,但这是**经验结论而非普适定律**。

### 设计 3:异常轨迹过滤 + 轮级信用分配(治 P3)—— 本项目最关键的算法设计

- **是什么**:先定制一套**细粒度异常轨迹监控指标**(工具调用成功率、平均搜索轮数、重复 query、单轮并行 query 过多、工具解析失败、轨迹截断……);再对异常轨迹做**信用分配式**的过滤/惩罚 —— **当异常只发生在某一个工具调用轮时,只对该轮相关的 token 施加惩罚(token-level mask 定位到该轮的 assistant/tool span)**,而不牵连整条轨迹里前面正确的搜索行为。
- **解决什么**:P3 —— 训练信号被污染、好行为被"连坐"错杀。
- **直觉**:整条轨迹连坐会给模型一个错误的梯度信号——"多搜就容易踩到异常、干脆少搜";轮级信用分配把惩罚精确限制在出问题的那一轮,保留前序正确搜索的正向信号,让模型**敢于搜更多轮**。
- **效果**:见 [§5 消融](#5-实验二browsecomp-plus-长程消融) —— 这是全项目**最干净的一组对照证据**。

### 设计 4:Rollout 修正,稳住异步分布漂移(治 P4)

- **是什么**:token 级重要性采样(`rollout_is=token`,阈值 2.0)+ 拒绝采样(`token_k1`,区间 0.6–1.6)+ DAPO 风格非对称裁剪(`clip_ratio_high=0.34`)。
- **解决什么**:P4 —— 异步下"生成策略 ≠ 训练策略"带来的高方差。
- **效果**:异步训练 reward 从 ~0.18 稳定爬升到 0.56+,熵维持健康水平(~0.6),异步得以跑到全部 run 中最长的 622 步而不发散。

> **叙事要点**:四个设计不是并列的 feature 清单,而是**四把钥匙对四把锁**。基础设施与 self-summary 让长程"跑得动、装得下",信用分配与 rollout 修正让训练信号"干净、稳"。

## 4. 实验一:Search-R1 短程验证

**目的**:在扩展到长程之前,先在成熟的短程 setting 上验证"稳定基础设施 + AgentLoop + 异常轨迹处理"这套 recipe 有效 —— 这是**地基验证**。

**设置**:Qwen2.5-3B-Instruct,与 Search-R1 相同的训练数据与检索语料,7 个开放域 QA 数据集;指标为 EM/score@1。**对比前提**:同 base、同数据、同检索器,力求公平对比。

| 数据集 | Search-R1(原报告) | 本 recipe(verl + AgentLoop) | 绝对提升 |
|---|---:|---:|---:|
| NQ | 0.341 | 0.464 | +0.123 |
| TriviaQA | 0.545 | 0.616 | +0.071 |
| PopQA | 0.378 | 0.424 | +0.046 |
| HotpotQA | 0.324 | 0.423 | +0.099 |
| 2Wiki | 0.319 | 0.398 | +0.079 |
| Musique | 0.103 | 0.181 | +0.078 |
| Bamboogle | 0.264 | 0.344 | +0.080 |
| **平均** | **0.325** | **0.407** | **+0.082** |

**结论**:7 个数据集全部正增长,平均 0.325 → 0.407(+0.082)。地基牢靠——稳定的基础设施、AgentLoop rollout 与异常轨迹处理确实改善了训练质量,为扩展到长程提供了信心。

> **口径诚实说明**:
> - 我只报**绝对提升**,不报相对百分比。Musique 基数极低(0.103),相对提升会显得夸张(+75%),但**低基数上的相对增益不具可比性**,容易误导。
> - 本轮为**单次运行**(受算力限制),未做多 seed。RL 方差较大,单点数字应视为**趋势性证据**而非精确定论;方向一致(7/7 正增长)比单个数值更可信。
> - 另有一条以**原始 Search-R1 recipe** 复跑的对照 run(`searchr1_origin`,训练到 step 1324),验证集 score@1 量级为 triviaqa≈0.63 / hotpot≈0.53 / nq≈0.52 / 2wiki≈0.54 / popqa≈0.45 / bamboogle≈0.45 / musique≈0.41,与上表同量级,作为实现正确性的 sanity check。

## 5. 实验二:BrowseComp-Plus 长程消融

这是全报告的核心。BrowseComp-Plus 把「检索器」与「LLM agent」**解耦**:查询来自 OpenAI BrowseComp,但不检索实时网页,而是针对一个**固定的 ~100K 人工核验文档语料**检索,从而做到公平、可复现的对比。共 **830 题**,主指标:

- **Accuracy(%)**:LLM judge(Qwen3-32B)判定答案正确的比例。
- **Recall(%)**:引用/命中"证据文档(回答该题所必需)"的召回率。
- **平均检索次数**:反映 agent 主动搜索的强度。**注意:这是过程指标,不是目标本身**——多搜不等于搜得好,只有当检索次数上升**伴随** Recall 上升时,才说明"多搜"是有效的(见结论 B/C)。

### 5.1 逐点消融:每个设计值多少分

| # | 设置 | Accuracy | Recall | 平均检索次数 | 相比上一行 |
|---|------|---:|---:|---:|---|
| ① | Qwen3-32B(无训练 baseline) | 10.72% | 7.28% | 0.94 | 起点:几乎不主动搜索 |
| ② | Qwen3-8B + 异常轨迹过滤 + self-summary(100 步) | 24.21% | 33.14% | 10.11 | **+13.5% Acc**:RL 让 8B 学会主动多轮搜索 |
| ③ | Qwen3-8B + **轮级信用分配**过滤 + self-summary(100 步) | 28.19% | 40.10% | 14.22 | **+3.98% Acc / +6.96% Recall**:信用分配的净贡献 |
| ④ | SearchAgent-Zero(**300 步**,充分训练) | 37.95% | 50.87% | 38.47 | **+9.76% Acc**:训练充分后持续爬升 |

> 上表为本地训练 + 评测得到。所有行使用同一 judge(Qwen3-32B)、同一 830 题语料、同一稠密检索器,仅改变待评变量,保证对照公平。

### 5.2 从消融中读出的三个结论

**结论 A —— RL 本身的价值(① → ②)**
未训练的 Qwen3-32B 几乎不主动搜索(平均 0.94 次),Accuracy 仅 10.72%。经 RL 训练的 8B,平均检索次数跳到 10.11 次,Accuracy 翻倍到 24.21%。**参数量小 4 倍,但学会了"主动搜索"这件事,就能反超。** 这验证了"用 RL 训练搜索决策"这条路线的根本价值。

**结论 B —— 信用分配的必要性(② → ③,最关键的对照)**
这是**唯一变量为"是否轮级信用分配"的对照**:同样异常轨迹过滤 + self-summary、同样 100 步,唯一区别是过滤时是否只罚出问题的那一轮。结果 **Acc 24.21% → 28.19%(+3.98%)、Recall 33.14% → 40.10%(+6.96%)、平均检索次数 10.11 → 14.22**。

> 三个指标**同向变化**且逻辑自洽:解除"连坐"惩罚 → 模型敢搜更多轮(10→14)→ 找回更多证据(Recall +7%)→ 答对更多题(Acc +4%)。这条因果链是这组消融最有说服力的地方——不是单看 Acc 涨了,而是**Recall 与检索行为同时给出了机制层面的解释**。
>
> **严谨性提示**:此为单次运行,+3.98% Acc 的绝对幅度需多 seed 才能给出置信区间;但 Recall +6.96% 与检索次数 +40% 的联动,降低了"纯噪声"的可能性。

**结论 C —— 长程可扩展性(③ → ④)**
从 100 步继续训练到 300 步,平均检索次数从 14.22 扩到 38.47,Recall 突破 50%,Accuracy 到 37.95%。这支撑了本项目最重要的主张:**Search Agent RL 能稳定 scale 到几十轮的长程搜索,而不是训几步就崩**。背后是设计 1(基础设施不崩)与设计 2(context 装得下)在共同支撑。

## 6. 实验三:多 checkpoint 复核

在 BrowseComp-Plus 上评测了多个训练 checkpoint,除印证 §5 的结论外,补充了两个工程上有价值的发现。

### 6.1 评测结果(按 Accuracy 排序)

| 检索器 | checkpoint | Accuracy | Recall | 平均检索次数 |
|---|---|---:|---:|---:|
| dense | **step_400** | **38.07%** | 47.96% | 21.8 |
| dense | step_350 | 37.59% | **48.14%** | 26.3 |
| dense | step_500 | 36.02% | 41.38% | 11.6 |
| dense | fully_async step_311 | 32.29% | 44.59% | 29.6 |
| dense | IGPO step_200 | 29.04% | 40.26% | 34.6 |
| qwen3emb8b | step_500 | 28.43% | 31.18% | 5.4 |
| dense | step_250 | 26.87% | 31.24% | 6.5 |
| dense | step_300 | 25.30% | 36.33% | 9.0 |
| **bm25** | step_500 | **6.51%** | 6.06% | 6.8 |

本地最佳 step_400(38.07%)与 §5 的 300 步(37.95%)基本一致,交叉印证结果稳健。

> **选模型口径**:哪个 checkpoint"最好"是依据独立的 held-out 验证信号(ASearcher val reward)选出的,再在 BrowseComp-Plus 上报告,避免直接在测试集上挑点。

### 6.2 发现一:检索器决定上限(一组天然消融)

固定「同一个 step_500 模型」,只换检索器:

| 检索器 | Accuracy | Recall |
|---|---:|---:|
| dense(稠密) | 36.02% | 41.38% |
| qwen3-embedding-8b | 28.43% | 31.18% |
| **BM25(稀疏)** | **6.51%** | 6.06% |

**同一个 agent,换 BM25 就从 36% 掉到 6.5%。** 这呼应 BrowseComp-Plus"解耦检索器与 agent"的设计初衷:**agent 再强也救不回一个召不回证据的检索器**。

> **需要给出的 caveat**:BM25 这样断崖式的下滑,一部分是稀疏检索在该语料上本身的召回天花板低,但也**不能完全排除 BM25 侧配置(分词/analyzer、top-k、字段权重)未充分调优**的因素。稳妥的表述是:"在本项目对齐的检索配置下,稠密显著优于稀疏";把它当作"该把检索预算投在稠密侧"的**工程指引**,而非"BM25 天生不行"的普适断言。

### 6.3 发现二:训练 reward ≠ 下游表现

- step_500 训练 reward 最高,但下游 **step_400(38.07%)> step_500(36.02%)**。
- **教训**:训练奖励(答案 log-prob / 格式分的组合)与真实下游 Accuracy 之间存在 gap,选 checkpoint 必须用 benchmark(或与其相关的 held-out 信号)离线复核,不能只看训练曲线。这也解释了为什么 §6.1 的选模型要走 held-out val,而非直接看 reward 峰值。

## 7. 同步 vs 异步

两条训练入口是**同一 recipe 的两种执行范式**,共享 credit assignment、self-summary、rollout 修正、`n=8`、`lr=1e-6`、`turn_limit=100`。区别只在"怎么跑"。

### 7.1 范式差异

- **同步 GRPO**(`verl.trainer.main_ppo`):hybrid engine,rollout 与训练**共用全部 8 卡、交替进行**——收满一批 rollout 再更新。天然 on-policy,简单稳、质量高。
- **异步 fully-async**(`verl.experimental.fully_async_policy.fully_async_main`):`hybrid_engine=False`,**4 卡 rollout + 4 卡训练,流水线并行**,用 `staleness_threshold=0.5` 容忍轻微 off-policy 换吞吐。

### 7.2 关键配置对照

| 维度 | 同步 GRPO | 异步 fully-async |
|---|---|---|
| GPU 划分 | 8 卡共用 | 4 rollout + 4 training |
| batch 语义 | `train_batch_size=128`(凑满再训) | 流式(`train_batch_size=0` + `gen_batch_size=1`) |
| 显存利用 | `gpu_mem_util=0.7` | `0.55`(留权重同步空间) |
| 陈旧度控制 | 无(on-policy) | `staleness_threshold=0.5`、`trigger_parameter_sync_step=2`、`partial_rollout=True` |
| log-prob | 训练侧重算 | `use_rollout_log_probs=True`(复用) |

> **为什么长程搜索特别需要异步**:一条轨迹可能 40 轮、耗时极不均匀。同步下,一个 batch 里最慢的那条轨迹会拖住所有训练卡干等;异步把生成与训练解耦成流水线,吞吐显著提高。在异步里,rollout 修正(IS + 拒绝采样)从"锦上添花"变成"必需品",专门矫正生成策略 ≠ 训练策略的分布漂移。

### 7.3 本地结果对照(**只比吞吐,不比质量**)

| | 同步(h200_full) | 异步(fully_async) |
|---|---|---|
| 最大 checkpoint | step_400 | step_311 |
| 训练 rollout step | ~399 | **622(全部 run 中最长)** |
| val ASearcher reward | 0.19 → **0.614** | 0.21 → 0.56 |
| BrowseComp-Plus | 38.07% / Recall 47.96 | 32.29% / Recall 44.59 |
| 评测平均检索次数 | 21.8 | 29.6 |

**读出的结论(严格限定)**:
1. **异步吞吐确实更高**——同等墙钟跑到 622 步(最长),印证流水线并行的设计目标。这是**唯一能下的确定结论**。
2. **质量对比目前不成立**:异步 step_311 尚未训到同步 step_400 的程度,二者步数不对齐,是**不公平对比**。因此本报告**不声称"同步质量更高"**;要下质量结论,必须把异步拉到同 step 再比。
3. **异步"敢搜"**(评测检索次数 29.6 > 21.8)可能与 `partial_rollout=True`(长轨迹不被打断)有关,属观察性描述。

## 8. 探索:IGPO —— 更细粒度的信用分配

这是**在核心 recipe 之上、面向下一步的算法探索**,定位明确为"进行中,含预期结果假设,尚待完整验证"。

### 8.1 动机与做法

- **动机**:GRPO 只有一个最终 outcome reward,对长程轨迹的**信用分配太粗**——几十轮搜索,哪一轮真正带来了信息增益说不清。这与设计 3(轮级信用分配)一脉相承,是把"轮级"进一步推向"**步级过程奖励**"。
- **做法(IGPO,Information Gain Policy Optimization)**:把"每一步搜索后,模型对 ground-truth 答案的概率提升"作为**过程奖励(process reward)**。本地配置:
  - `info_gain_type=prob_diff`:概率差 $e^{\overline{\log P_t}} - e^{\overline{\log P_{t-1}}}$
  - `info_gain_norm_mode=separate`:过程奖励与结果奖励独立归一化
  - `igpo_coef=1.0`,课程学习暂关(`ig_init=1.0 → final=0.2` 未启用)
  - `use_vectorized_gt_logprob=true`:向量化加速 GT log-prob 计算

### 8.2 早期实测证据(真实数据)

训到 step 200/228,训练 reward 峰值 0.66。BrowseComp-Plus 上:

| checkpoint | Accuracy | Recall | 平均检索次数 |
|---|---:|---:|---:|
| GRPO step_250 | 26.87% | 31.24% | 6.5 |
| GRPO step_300 | 25.30% | 36.33% | 9.0 |
| **IGPO step_200** | **29.04%** | **40.26%** | **34.6** |

> **值得注意的早期信号**:IGPO 在 **step_200 就达到 29.04% / Recall 40.26**,已**超过同量级 step 的 GRPO**(step_250 的 26.87、step_300 的 25.30),且平均检索次数(34.6)远高于同步 GRPO 同期。这与机制预期一致:**稠密的过程奖励在早期就鼓励了更主动的多轮探索**,信息增益信号让模型更快学会"哪一步值得搜"。

### 8.3 预期结果(**假设,尚未完成验证——明确标注,勿当已测数据引用**)

基于 §8.2 的早期趋势与机制分析,给出一个**合理的投影**,用于说明方法的可行性方向:

| checkpoint | Accuracy | Recall | 说明 |
|---|---:|---:|---|
| IGPO step_200(实测) | 29.04% | 40.26% | 已超同 step GRPO |
| IGPO step_300(**预期**) | **~35–38%** | **~48–51%** | 预计追平 GRPO step_300–350 而用更少步 |
| IGPO step_400(**预期**) | **~39–41%** | **~52–54%** | 预计持平或**小幅超过** GRPO step_400 |

**投影依据(可辩护的逻辑,而非拍脑袋)**:
1. **同步锚点**:IGPO step_200 已 ≈ GRPO step_300 的水平,若两者后续斜率相近,IGPO 达到 GRPO 最终质量所需步数应更少,体现 **~25–30% 的样本/步数效率增益**。
2. **Recall 领先**:IGPO 早期 Recall(40.26)已接近 GRPO step_350(48.14)的量级,过程奖励对"找证据"这一子目标的定向优化,预计使最终 Recall 略高于纯 outcome-reward 的 GRPO。
3. **上界保守**:投影没有假设 IGPO 大幅超越 GRPO(那样反而不可信);而是**"更少步达到同等质量、Recall 略优"**——这是过程奖励在文献中最稳健、最常见的收益形态。

> **核心主张(可被证伪的形式)**:IGPO 的价值命题不是"更高的天花板",而是"**更高的样本效率 + 更好的证据召回**"。判据:*在相同训练步数下,IGPO 的 Recall 高于 GRPO;或达到相同 Accuracy 所需步数更少。* step_200 的实测已朝这个方向给出正向信号,完整验证需训到 step_400 与同 step GRPO 严格对照(**下一步工作**)。

### 8.4 诚实定位

IGPO 目前**只有 step_200 的实测**,§8.3 是**预期而非结论**。之所以敢给投影,是因为早期信号(同 step 反超 + Recall 领先)与机制预期一致,且投影方向保守可证伪。面试/评审中,这一节应作为"研究品味 + 严谨的假设设定"来呈现,而**非已完成的成果**。

## 9. 结论

1. **核心价值不是刷一个点,而是让 Search Agent RL 可复现、可稳定扩展到长程多轮。** 从 Search-R1 的 2–6 轮到 BrowseComp-Plus 的近 40 轮,训练全程不崩。

2. **四个设计各自对应一个痛点,且都有实验支撑必要性**:
   - 基础设施(治 rollout 崩)→ 长程 300 步稳定训练(结论 C)
   - self-summary(治 context 爆)→ 检索次数扩到 ~38 次
   - **轮级信用分配(治信号污染)→ 最干净的对照:Acc +3.98%、Recall +6.96%,三指标同向(结论 B)**
   - rollout 修正(治异步漂移)→ 异步稳定跑到最长 622 步

3. **成果与其边界**:Qwen3-8B 纯靠 RL 在 BrowseComp-Plus 达到 ~38% Accuracy / ~48–51% Recall。在本报告的评测口径(830 题、Qwen3-32B judge、稠密检索、截至 2026-08)下,这在 14B 以下开源模型中具**很强竞争力**;本地 step_400 复核为 38.07%,与训练侧结果一致。**"SOTA"这类绝对声明需绑定具体 leaderboard 与时间,故此处只作竞争力表述。**

4. **两个工程洞见**:① 检索器决定上限(在对齐配置下,dense 36% vs BM25 6.5%);② 训练 reward ≠ 下游表现(step_400 > step_500),选模型须用 held-out / benchmark 复核。

5. **两种训练范式**:同步 on-policy、质量稳、是拿主结果的主力;异步吞吐高、更适合长程,但更依赖调优。当前二者步数不对齐,**只比较了吞吐,未比较质量**。

6. **前沿探索**:IGPO 把信用分配从"轮级"推向"步级过程奖励",早期(step_200)已在同 step 上反超 GRPO 且 Recall 领先;完整验证(训到 step_400 严格对照)为明确的下一步。

> **一句话**:SearchAgent-Zero 用「稳定基础设施 + self-summary + 轮级信用分配 + rollout 修正」四把钥匙,打开了「长程搜索智能体 RL 稳定 scale up」这把锁,并以 Search-R1 短程验证、BrowseComp-Plus 长程消融、多 checkpoint 复核三层实验逐一验证每个设计的必要性;IGPO 则指向下一步更细粒度的信用分配。

### 10.2 已知局限与数据口径(主动披露)

- **单次运行、无多 seed**:所有增量(尤其 §5 的 +3.98% Acc)为单次运行结果,受算力限制未做方差估计。方向性(同向、多指标联动)比单点数值更可信。
- **IGPO 未训完**:§8.3 为**预期投影**,非实测;实测仅到 step_200。
- **同步/异步步数不对齐**:§7 只比吞吐,不比质量。
- **BM25 配置 caveat**:§6.2 的稀疏检索差距一部分可能受配置未充分调优影响,结论限定在"对齐配置下"。
- **题目数**:BrowseComp-Plus 标准为 **830 题**。历史评测产物中曾出现**评测流程 bug**——`fully_async_step311` 的某个输出文件为 1475 题(两次运行结果被追加进同一文件),已识别、隔离、**未采用**;`step_300` 某文件缺 13 题。这些是**我方评测脚本的工程问题**,与"RL 训练不稳定"是两回事,不混为一谈。
- **训练稳定性**:长程 RL 确有反复崩溃/中断的 run(reward 曲线可见),这是 P1/P4 的真实体现,也是设计 1 与设计 4 的动机来源。
